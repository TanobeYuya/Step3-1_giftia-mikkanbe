# spec-gate — 実装に入る前の確認

正本文書は `.claude/project.json` の `docs.canonical`（上ほど優先）、実装計画は `docs.plan`。

## 着手してよいか

1. 対象の作業に対応する文書 ID（要件・仕様・設計・テスト設計）を正本文書から特定する。見つからなければ「仕様に書かれていません」と報告して止まる。
2. 実装開始の承認記録（計画のコミットや PR に残った「OK、進めて」）があるかを確認する。会話で口頭の確認しかなく、対象の版がはっきりしない場合は、計画を示して承認を求める。
3. 未決の項目が含まれていれば、その部分は作らない。進めるよう指示されても、未決の部分は補わない。
4. Issue が必要な種類の作業（`git.issueRequiredFor`）で Issue がなければ、gh-flow スキルの手順で起票する。

## 実装中

- 良かれと思って機能・API・テーブル・設定を足さない。足したくなったら提案だけして止まる。
- 仕様に数式で書かれた計算（閾値・判定式など）は、そのまま実装する。言い換えたり、より良い式に置き換えたりしない。変えたい場合は提案だけする。
- 「今日の日付」や乱数は関数の中で取得せず、引数で受け取る（テストが実行日に依存しないようにする）。
- テストが失敗したら、期待値を書き換えて通さない。実装を直すか、止まって報告する。承認済みの評価基準（テスト設計）は、再承認なしに変えない。
- テスト設計の作成者と承認者を同じ人にしない。

## 完了報告

- `/evidence` でテストとビルドを実行し、ログのパスを添える。
- 参照した一次情報（文書 ID、確認したライブラリのバージョン、読んだソースのパスと行）を書く。
- 機能を追加したあとは、既存の回帰テストを全件実行する。
