作業ブランチの差分を、PR を出す前の事前レビューとしてレビューしてください。あなたは実装した本人ではありません。実装者の意図を好意的に補わず、文書と規約だけを根拠にしてください。

## 手順

0. 追加の指示の先頭がディレクトリのパス（例: `.claude/state/template-work`）なら、そのリポジトリを対象にする。以下の git コマンドは `cd <パス> && …` の形で実行し、ファイルのパスもそのリポジトリを基準に読む。
1. 対象リポジトリの `.claude/project.json` を読み、`git.baseBranch`（以下 base）と `docs.canonical` を確認する。
2. `git fetch origin <base>` のあと、`git diff origin/<base>...HEAD` と `git log origin/<base>..HEAD --oneline` で差分とコミットを読む。
3. 正本文書のうち、差分に関係する節を読む。`CLAUDE.md` と `.claude/rules/` のうち、差分のパスに当たるものも読む。
4. 次の観点で確認する。
   - 正本文書との一致（仕様にない機能・API・テーブル・設定が足されていないか、数式が書き換えられていないか）
   - 秘密情報、デバッグ用の残骸、無関係な変更が混ざっていないか
   - ロジックの変更にテストがあるか。テストの期待値が、理由なく書き換えられていないか
   - コミットメッセージとブランチ名が `git` の規約に合っているか
   - PR 本文に書くべき ID と証拠がそろっているか（そろっていなければ、何が足りないかを書く）
   - 変更した文書（.md 等）の日本語が `.claude/rules/japanese-writing.md` に沿っているか（不自然な箇所は「推奨」として挙げ、`ja-polish` での修正を勧める）
5. 結果を、対象リポジトリの `.claude/state/reviews/<git rev-parse HEAD の値>.md` に保存する。このディレクトリ以外には書き込まない。コードは直さない。

## 記録の形式（1行目は必ずこのどちらか。フックが読む）

```
判定: 要対応なし
```

または

```
判定: 要対応あり
```

2行目以降に、対象のコミット、日時、指摘の表（対象（ファイル:行）／指摘／根拠 ID／重さ）を書く。重さは、要対応・推奨・参考の3段階。「要対応」が1件でもあれば、判定は「要対応あり」にする。

## 返す内容

判定、要対応の一覧、記録ファイルのパス。PR 本文の「事前レビュー」欄にそのまま貼れる、3〜5行の要約。

追加の指示: $ARGUMENTS
