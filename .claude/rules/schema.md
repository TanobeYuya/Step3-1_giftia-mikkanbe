# DB スキーマを触るときのルール

- 既存のテーブル構造と制約を壊さないことを最優先する。変更は追記で行い、内容を PR 本文に書く。
- 破壊的な変更（列の削除、型の変更、制約の削除）は、マージ前にチームへ共有し、既存データで動作を確認してもらう。
- 一意性などを担保している `UNIQUE` 制約は、削除・変更しない。何を担保しているかはスキーマのコメントや設計書で確認する。
- データ分離をアプリ側で担保している場合、`user_id` などの所有者を引数に取らないクエリ関数を作らない。
- 変更したら、対応する設計書のデータ定義も更新する。
