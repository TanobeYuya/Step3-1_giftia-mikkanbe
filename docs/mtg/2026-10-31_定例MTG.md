## 議論の要点

### 1. ターゲットの選定

- あかぷさん：送別会の購入を優先する案。購入率が最も低く、注文単価が大きい。購入率が 0.1 ポイント上がると、売上は約 449 万円増える試算。ただし、友人・家族の誕生日ではなく送別会を選ぶ根拠と、アプリで解決できるかの検証はまだ足りない。
- べー：売上への影響が最も大きいセグメントを優先する案。友人への誕生日（セッション構成比 29%）と家族への誕生日（平均注文単価 5,400 円）が大きい。送別会の購入率 1.7% は、他サイトと比べられないので低いとは言い切れない。比較の基準は、構成比・単価・購入率を掛け合わせた売上への影響にする。
- みかんさん：送別会の悩みは「相手の好みが分からず決めきれない」ことで、Giftia の仕組みで解決できるか迷う。友人・家族の誕生日のように「探す段階で見つけにくい」課題のほうが、改善しやすい。
- 班長の判断案：全員が重要とした B（友人の誕生日）と、売上規模が2番目に大きい D（家族への誕生日）から始める。最終決定は Slack での議論のあと。

### 2. 運用ルール（CLAUDE.md）

- 計画は人が立てて3人で合意し、AI は実装の段階でだけ動かす。
- 仕様書・要件定義書に書かれていないものは、AI に作らせない。
- 結果は証拠を残す。テストが失敗しても、期待値を書き換えない。
- `.env` は読み書きさせない。フックと settings.json の deny で止めている。`rm` などの削除も deny で止めている。
- 作業の難しさに合わせてモデルを使い分け、費用を抑える。
- 補足（べー）：エラーメッセージには個人情報が含まれないので、AI にそのまま貼ってよい。ファイルを読む許可の確認は、基本的に許可してよい。

### 3. 環境構築のつまずき

- MySQL Workbench は、新しいバージョンを入れると接続できないことがある。配布資料にバージョンの指定がない。
- API の組み込みで 500 エラーが続いた例があった。
- つまずいた点とエラーの対応は、メンバー同士で共有して助け合う。
