## 0. この書類の使い方

### 0.1 位置づけ

要件定義書が「何を作るか」を決め、この書類は「どうふるまい、どう作るか」を決める。番号は次のようにつながる。

```text
要求（BR）→ 要件（FR・DR・NFR）→ 仕様（SP）→ 設計（DS）→ テスト（TC）→ Issue
```

どの仕様・設計も、答える要件と要求を「対応」の欄に書く。要件にたどれない仕様・設計は作らない。

### 0.2 実装する人（AI を含む）へ

この書類だけで、Issue の作成から PR までを通せる粒度で書いている。実装するときは次を守る。

1. 読む順：0章 → 担当する Issue（6章）→ その Issue が指す SP と DS → 7章の手順。
2. この書類と要件定義書に書いていない機能・API・テーブル・列・設定は作らない。必要だと思ったら、作らずに「仕様に書かれていません」と報告して止まる。
3. `【MTG】` の仮決めが MTG で変わった場合は、この書類が更新されてから実装する。
4. 班の DB への書き込み（DS-01 の SQL）は、AI が実行しない。人がチームの了承を得てから実行する。
5. テストは 0.3 のとおりに扱う。

### 0.3 テストの扱い（コードをテストに合わせる。テストをコードに合わせない）

5章のテストケース（TC）は、実装より先に決めた「合格の基準」である。実装は TC を通すために書く。TC を実装に合わせて変えることは、理由があっても実装の PR の中では行わない。

してはいけないこと

| してはいけないこと | 例 |
| --- | --- |
| 期待する結果を、実装の結果に合わせて書き換える | TC-13 の「rows＝312」を、出た値の「310」に直す |
| 合格の条件をゆるめる | 「全件が『誕生日』を持つ」を「上位10件が持つ」に変える。「5個以下」の確認を外す |
| TC を飛ばす、確かめていない TC を合格と書く | 時間がないので TC-11 を「未実施」にせず「OK」と書く |
| テストの入力にだけ合う作り方をする | TC で使う商品ID や検索語のときだけ、特別な値を返すように書く |
| 確かめる対象を置き換える | DB の代わりに固定の値を返す仮の関数を使い、それで合格とする |
| 失敗を隠す | 失敗した TC を報告に書かない。エラーを握りつぶして空の結果を返す |

TC が通らないとき

1. まずコードを直す。
2. それでも通らず、TC のほうが間違っていると考えるとき（例：DB の実データが 1.2 と違っていた）は、実装を止める。そして、通らない TC、実際の結果、TC が間違っていると考える理由を、Issue にコメントして報告する。
3. TC を変えるのは、この書類を直す別の PR だけにする。その PR で、作成者以外の Approve を受けてから実装に戻る。
4. 実装の PR には、通らなかった TC を「失敗」のまま書く。「失敗」を残したまま PR をマージしない。

## 3. 仕様（外から見たふるまい）

### SP-01 贈る相手を選べる

- 対応: FR-01 ／ BR-01・BR-02
- 「いまの検索」タブに、贈る相手のプルダウンを出す。
- 選択肢は「指定なし」（既定）と「母（義母を含む）」の2つ【MTG】。
- 「指定なし」のときは、API に recipient を送らない。「母（義母を含む）」のときは `recipient=mother` を送る。
- 「取引先へのお礼」タブには出さない。このタブで検索したときは recipient を送らない。

### SP-02 シーンを選べる

- 対応: FR-02 ／ BR-01・BR-02
- 「いまの検索」タブに、シーンのプルダウンを出す。
- 選択肢は「指定なし」（既定）と、9種類のシーン。並び順は、誕生日・送別・お礼・母の日・お歳暮・お中元・結婚祝い・父の日・出産祝い（在庫ありの商品が多い順。1.2）。
- 「指定なし」のときは、API に scene を送らない。選んだときは `scene=誕生日` のように、シーンの名前をそのまま送る。
- 「取引先へのお礼」タブには出さない。

### SP-03 絞り込めることが分かる見出しを出す

- 対応: FR-05 ／ BR-01
- 贈る相手のプルダウンの上に「誰に贈る？」、シーンのプルダウンの上に「どんな場面？」と出す。
- 見出しとプルダウンは、クリックで連動する（見出しを押すとプルダウンにフォーカスが移る。HTML の label）。

### SP-04 シーンで絞り込む

- 対応: FR-03 ／ BR-02
- シーンを選ぶと、結果はそのシーンのタグを持つ商品だけになる。total（該当件数）も、絞り込んだあとの件数にする。
- いまの条件（在庫あり・キーワード・カテゴリー）と組み合わせる（AND）。
- 贈る相手では絞り込まない（SP-05）。

### SP-05 贈る相手で並べ替える

- 対応: FR-03 ／ BR-02（要件定義書 6.2）
- 贈る相手を選んだとき：① その相手に贈ったレビューの件数が多い順 → ② 販売数の多い順 → ③ 商品IDの順。件数のデータがない商品は0件として扱い、後ろに並ぶ。
- 贈る相手を選ばないとき：いまと同じ（② → ③）。
- total は、贈る相手を選んでも変わらない（絞らないため）。

### SP-06 結果カードにタグを出す

- 対応: FR-04 ／ BR-01・BR-02（要件定義書 6.3）
- 各カードに、タグを0〜5個出す。同じタグを2回出さない。「おすすめ」という文字は出さない。
- タグの系統と名前

| 系統 | 出す条件 | タグの名前 | 系統ごとの上限 |
| --- | --- | --- | --- |
| 贈る相手 | その相手のレビュー件数が1以上 | 「母 3件」（相手の短い名前と件数）【MTG】論点 #3 | 2個 |
| シーン | 商品がそのシーンのタグを持つ | 「誕生日」など、シーンの名前 | 3個 |
| 商品の性質 | room_temp＝1 | 「常温」 | 3個 |
| 〃 | indiv_wrap＝1 | 「個包装」 | 〃 |
| 〃 | shelf_life_days がある | 「日持ち30日」（日数を入れる） | 〃 |

- 並べる順
  1. 検索で選んだ贈る相手のタグ（あれば）
  2. 検索で選んだシーンのタグ（あれば）
  3. 残りの贈る相手のタグ（件数の多い順）
  4. 残りのシーンのタグ（SP-02 の選択肢の順）
  5. 商品の性質のタグ（常温 → 個包装 → 日持ち の順）
- 系統ごとの上限を超えたものは捨てる。全体で5個を超えたら、後ろから捨てる。
- 「取引先へのお礼」タブの結果にも、同じ規則でタグを出す（選んだ相手・シーンがないので、1と2は空になる）。

### SP-07 決めた値以外は受け付けない

- 対応: 要件定義書 4.3（決めた値以外は 422）、8章 セキュリティ ／ BR-02
- recipient が空か `mother` 以外、scene が空か9種類以外のときは、HTTP 422 を返し、検索しない。
- 画面はプルダウンなので、通常の操作では 422 にならない。URL を直接書き換えたときの防御。

### SP-08 いまの動作を変えない

- 対応: 要件定義書 6.4 No.4 ／ BR-02
- 贈る相手もシーンも選ばないときの「いまの検索」の結果（件数・並び順）は、変更前と同じ。タグが増えることだけが違う。
- 「取引先へのお礼」タブの入力と結果は、タグが増えることを除いて変えない。
- API につながらないときの「APIにつながりません」の表示も変えない。

### SP-09 贈った相手ごとのレビュー件数を持つ

- 対応: DR-01 ／ BR-01・BR-04（要件定義書 5.2）
- product_facts に、fact＝`review_to_mother` の行を持つ。value は、母・義母に贈ったと書かれたレビューの件数（1以上）、source は `review_rule`。
- 「母・義母に贈った」とは、レビュー本文に「母」を含み、「祖母」「叔母」「伯母」を含まないこと。
- 件数が0の商品には行を作らない。
- 期待する結果：312行、value の合計 425（1.2）。

### SP-10 同じ SQL で作り直せる

- 対応: DR-02 ／ BR-04
- データを作る SQL は、何回流しても同じ結果になる（前回の行を消してから入れ直す）。
- 新しいレビューが増えたら、同じ SQL を流し直すだけで更新される。

### SP-11 付け方の精度を確かめる

- 対応: NFR-01 ／ BR-01
- 「母・義母に贈った」と判定したレビューから、無作為に20件を人が読み、誤り（母・義母以外に贈ったもの）が2件以下であること。

## 4. 設計（どう作るか）

### DS-01 データ作成の SQL

- 対応: SP-09・SP-10・SP-11 ／ DR-01・DR-02・NFR-01
- ファイル: `giftia/backend/sql/001_review_to_mother.sql`（新規）
- 実行: MySQL Workbench で、班の DB に接続して流す。AI は実行しない。流す人は、事前に Slack で班の了承を得る（共有DBへの書き込みのため）。
- 中身（このまま使う）

```sql
-- 001_review_to_mother.sql
-- 目的: 商品ごとに「母・義母に贈ったと書かれたレビューの件数」を product_facts に入れる（DR-01）
-- 何回流しても同じ結果になる（DR-02）。必ず giftia_t103 を付ける（他の班の DB を変えないため）
-- 実行: MySQL Workbench で、このファイルを全部選んで実行する

SET SQL_SAFE_UPDATES = 0;  -- Workbench の安全モードは、主キーの先頭列を使わない DELETE を止めるため、一時的に外す
START TRANSACTION;

DELETE FROM giftia_t103.product_facts
WHERE fact = 'review_to_mother';

INSERT INTO giftia_t103.product_facts (product_id, fact, value, source)
SELECT r.product_id, 'review_to_mother', COUNT(*), 'review_rule'
FROM giftia_t103.reviews AS r
WHERE r.comment LIKE '%母%'
  AND r.comment NOT LIKE '%祖母%'
  AND r.comment NOT LIKE '%叔母%'
  AND r.comment NOT LIKE '%伯母%'
GROUP BY r.product_id;

COMMIT;
SET SQL_SAFE_UPDATES = 1;

-- 確かめる（期待: rows=312, total=425）
SELECT COUNT(*) AS `rows`, SUM(value) AS total
FROM giftia_t103.product_facts
WHERE fact = 'review_to_mother';
```

#### DS-02-2 引数（`search()` に2つ足す）

- `scene: Literal["", "誕生日", "送別", "お礼", "母の日", "お歳暮", "お中元", "結婚祝い", "父の日", "出産祝い"] = Query(default="", ...)`
- `Literal` は `typing` から読み込む。FastAPI は、Literal にない値を受け取ると自動で 422 を返す（SP-07）。自前のチェックは書かない。
- Literal の中身と、DS-02-1 の定数は一致させる。

#### DS-02-3 件数と商品の取得

1. いまの WHERE の組み立ては変えない。FROM を `products AS p` にし、列名はいまのまま（product_facts と名前が重なる列は WHERE で使っていない）。
2. scene があれば、WHERE に次を足す（SP-04）。

   ```sql
   EXISTS (SELECT 1 FROM product_scenes AS s WHERE s.product_id = p.product_id AND s.scene_tag = %s)
   ```

3. 件数：`SELECT COUNT(*) AS n FROM products AS p WHERE {condition}`（いまと同じ形）。
4. 商品：recipient があるときだけ product_facts をつなぐ（SP-05）。

   ```sql
   -- recipient あり
   SELECT p.product_id, p.category, p.brand, p.product_name, p.price, p.rating, p.review_count
   FROM products AS p
   LEFT JOIN product_facts AS f ON f.product_id = p.product_id AND f.fact = %s
   WHERE {condition}
   ORDER BY COALESCE(f.value, 0) DESC, p.sales_count DESC, p.product_id
   LIMIT %s
   -- %s の順: RECIPIENTS[recipient]["fact"], WHERE の値..., limit

   -- recipient なし（いまと同じ並び順。SP-08）
   ... FROM products AS p WHERE {condition} ORDER BY p.sales_count DESC, p.product_id LIMIT %s
   ```

5. 値はすべて `%s` で渡す。SQL の文字列に値を直接つなげない（要件定義書 8章）。

#### DS-02-4 タグの取得と組み立て

1. タグの取得は、商品を取得したあとに2回だけ流す（商品ごとには流さない。N+1 を避ける）。結果が0件なら流さない。

   ```sql
   SELECT product_id, scene_tag FROM product_scenes WHERE product_id IN (%s, %s, ...)
   SELECT product_id, fact, value FROM product_facts
   WHERE product_id IN (%s, %s, ...)
     AND fact IN ('room_temp', 'indiv_wrap', 'shelf_life_days', <RECIPIENTS の fact すべて>)
   ```

   IN の `%s` の数は、商品の数に合わせて組み立てる。fact の一覧も `%s` で渡す。
2. 関数 `build_tags(scenes: list[str], facts: dict[str, int], recipient: str, scene: str) -> list[dict]` を作る。DB を呼ばない純粋な関数にする。
3. 中身（SP-06 の順）

   ```text
   recipient_tags = [RECIPIENTS の各相手 k について facts[fact_k] >= 1 なら {"kind":"recipient","name":tag_k,"count":facts[fact_k]}]
                    → 選んだ相手を先頭、残りは count の多い順 → 先頭から TAG_LIMITS["recipient"] 個
   scene_tags     = [SCENES の順に、商品が持つシーンを {"kind":"scene","name":名前}]
                    → 選んだシーンを先頭 → 先頭から TAG_LIMITS["scene"] 個
   fact_tags      = room_temp==1 なら「常温」、indiv_wrap==1 なら「個包装」、shelf_life_days があれば「日持ち{値}日」
                    → 先頭から TAG_LIMITS["fact"] 個（kind は "fact"）
   選んだもの     = recipient_tags の先頭が選んだ相手なら取り出す ＋ scene_tags の先頭が選んだシーンなら取り出す
   tags = 選んだもの ＋ 残りの recipient_tags ＋ 残りの scene_tags ＋ fact_tags → 先頭から TAG_MAX 個
   ```

4. `to_gift(r)` に `tags` を足して返す。

#### DS-02-5 応答

要件定義書 4.3 の例のとおり。`tags` の要素は `{"kind": "recipient" | "scene" | "fact", "name": str, "count": int}`。`count` は kind が recipient のときだけ付ける。

# review_text.py — レビュー本文を文に分ける（SP-19・10.1 論点2）。tools/sentences.py と main.py の両方で使う
import re

_PIECE = re.compile(r"[^。]+。?|。")  # 「。」までを1つのかたまりとして取る（「。」がない最後の文も取る）


def split_pieces(comment: str) -> list[tuple[str, str]]:
    """本文を (表示する文字列, 辞書のキー) の並びに分ける。表示する文字列をつなげると原文に戻る"""
    pieces = []
    for m in _PIECE.finditer(comment):
        text = m.group(0)
        key = text.rstrip("。").strip()
        pieces.append((text, key))
    return pieces
```

# database.py に足す
from contextlib import contextmanager


@contextmanager
def connection():
    """接続を1つ作り、with の中で使い回す。抜けるときに必ず閉じる"""
    conn = get_connection()
    try:
        yield conn
    finally:
        conn.close()


def fetch_all(query: str, params: tuple = (), conn=None) -> list[dict]:
    """conn を渡せばその接続で実行する。渡さなければ、いままでどおり1回だけの接続を作る"""
    if conn is None:
        with connection() as c:
            return fetch_all(query, params, c)
    with conn.cursor() as cur:
        cur.execute(query, params)
        return cur.fetchall()
```
