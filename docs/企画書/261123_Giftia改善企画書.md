## 0. 一言と、今日決めていただきたいこと

### 一言（スライド用）

> Giftia で相手に合う商品を決めきれない人に、相手との思い出を問いかけ、決め手を引き出す。

### 定義（企画書・定義書用）

> Giftia で贈り物を選ぶ人が、相手に合う商品を決めきれずに離脱する課題を、Giftia が相手との過去の会話や場面を問いかけ、思い出してもらった相手の情報を決め手にすることで解決する。

| 枠 | 中身 |
| --- | --- |
| 誰の | Giftia で贈り物を選ぶ人。解く範囲は、決め手が記憶にある「思い出し型」。最初の検証は家族への誕生日から |
| 何の課題 | 決め手は「相手についての情報」。記憶にあるのに、選ぶ場では思い出せず、人気に頼って離脱する |
| どう解く | Giftia が相手について問いかける「相談モード」で決め手を思い出してもらい、Giftia の商品につなぐ |
| Giftia にとって | 家族への誕生日の購入率を 2.3% から 3.0% に上げる |

### 決めていただきたいこと

> 家族への誕生日で相談モードを作り、3か月の A/B テストを行う投資を承認してほしい。条件は、PoC で「思い出せる」「商品に結べる」の兆しが出ること。あわせて、撤退ラインと判定者（案：副社長）を合意してほしい。

| 関門 | 判断 | 損はどこまでか |
| --- | --- | --- |
| G0 PoC（着手中） | 兆しが出なければ作らない | 班の数日分 |
| G1 A/B テスト（3か月） | 今より有意に改善し、増える売上が運用費を上回れば残す。届かなければ撤退 | 開発費（開発部の見積もり待ち） |
| G2 広げる判断 | 3.0% に届けば他の相手・場面に広げる | 改善の工数 |

詳しい線は4章。PoC はアプリを使わないため、承認を待たずに班で着手している。結果は発表で報告する（結果が出る日は未定）。

## 1. 事実：何が起きているか

### Giftia の数字（Exhibit 1）

- セッション 375万 → 480万（+28%）に対し、売上は 6.41億 → 6.91億円（約 +8%）
- 購入率 3.6% → 3.0%、購入までの日数 1.8 → 3.1日
- 詳細を見た商品は 6.2 → 9.4商品に増えたのに、カート投入率は 12% → 8% に下がった
- CS の問い合わせの最多は「商品の選択・用途」31%。「見つからない」は 4%、検索結果0件率は 2.1%

**人は来て、商品も多く見ているのに、選べずに帰っている。** 品揃え不足や流入経路は、主因とは読みにくい。

### 顧客の言ったことと、実際の決め手

| 人 | 言ったこと | 実際の決め手 | 出典 |
| --- | --- | --- | --- |
| D さん（母への誕生日） | 母の年代で人気のものが分かると助かる。「何も手掛かりがないから、まず人気を見る」 | ランキングでは決められず離脱。数日後、母の「こういうの便利そうね」を思い出し、ランキング外の電気ケトルを購入 | Exhibit 2 |
| 班のメンバー | — | 去年あげたものと被らないこと | 2026-11-22 レビュー会（体験） |
| 班のメンバー | — | 相手が使っている物が壊れている・古い（割れたポット、20年使っている） | 同上（体験） |
| 班のメンバー | — | 好みの細かいところ（ブランド・色・香り） | 同上（体験） |
| 40代女性（友人への誕生日） | 「こういう人にはこの商品」がすぐ分かれば、すぐ買えるかもしれない | 化粧品の種類・ブランド・付き方を、本人や共通の友達に聞いてそろえてから決める | 班のヒアリング |

**言ったこと（人気が知りたい）と、実際の決め手（相手の一言）がずれている。** D さんは手がかりを持っていたのに、手がかりだと自覚していなかった。

## 2. 課題：誰の、何の課題か

決め手は、どの話でも「相手についての情報」だった（相手の一言、過去の贈り物、今使っている物の状態、好みの細かいところ）。その情報は贈り手の記憶にあるか、人に聞けば手に入る。しかし Giftia の中には、それを思い出させる仕掛けがない。そのため、商品を多く見ても決めきれず、人気に頼って離脱する。

**顧客の課題と Giftia の課題は、1本でつながる。** 顧客が決めきれない → 離脱する → 購入率が下がる。顧客が決めきれるようになれば、購入率が上がる。

### 誰の：課題は広く、解く範囲は狭く

| 層 | 範囲 | 理由 |
| --- | --- | --- |
| 課題の定義 | Giftia で贈り物を選ぶ人 | D さん1人の課題では、Giftia の課題（購入率、選択の問い合わせ 31%）が解けるとは限らない |
| 解く範囲 | 思い出し型：決め手が自分の記憶にある人 | 問いかけで直接取りに行ける |
| 最初の検証 | 家族への誕生日 | 数字がそろっている（購入率 2.3%、構成比 24%、単価 5,400円）。D さんは典型例として使う |

今回やらないのは、人に聞きに行く人（40代女性のように、本人や友達に聞いて情報をそろえる人）。決め手が記憶ではなく他人にあるため、問いかけでは取りに行けない。

### 課題ではないもの

- 商品が見つからない、ではない（0件率 2.1%。ケトルも Giftia にあった）
- 何がいいか分からない、ではない（答えは記憶にあった）
- 人気が分からない、でもない（人気を見ても決められなかった）

### 提供価値と要求

**提供価値**：贈り物を選ぶ人が、Giftia の中で相手についての情報を思い出し、「この人に合う」と決めきれる。

| ID | 区分 | 要求 | 優先度 |
| --- | --- | --- | --- |
| BR-01 | 顧客要求 | 商品を選んでいる間に、相手についての情報（一言・過去の贈り物・今使っている物・好み）を思い出せる | 高 |
| BR-02 | 顧客要求 | 思い出した情報を決め手にして、「この人に合う」と思える商品を選べる | 高 |
| BR-03 | 事業要求 | 家族への誕生日の購入率を 2.3% → 3.0%（全体平均）に上げる。3.0% は班が置いた目標 | 高 |
| BR-04 | 事業要求 | 新商品が増えても、商品部（月5人日）と編集（月10人日）の工数で続けられる | 中 |

※ 要求定義書の BR-01・BR-02 の言い方は、別の PR で直す（9章）。

## 3. 仮説検証のストーリー：試して、分かって、次へ

### 最初の仮説：同じ境遇の人の買い物を見せれば、思い出せる

最初は、安く速く確かめられる順に試す計画で始めた。いまあるレビューやタグと画面で試せる打ち手から作った。

| 段 | 作ったもの | 結果 |
| --- | --- | --- |
| Phase1 タグ付け（実装済み） | 「誰に贈る？」「どんな場面？」のプルダウン。母へのレビューが多い順。結果カードのタグ | 「母 12件」のタグは安心にはなるが、思い出すきっかけにはならなかった |
| Phase2 モーダル（実装済み） | カードを押すとモーダル。母に贈った人のレビューを先頭に、使う場面の文をハイライト | 母に贈ったレビュー 97件に、母の発言は0件。他人の使用感では、相手本人の情報にならなかった |

### 分かったこと：足りないのは、商品の情報ではなく相手の情報

並行したヒアリングでも、決め手は全員「相手についての情報」だった。他の人の買い物やレビューをいくら見せても、相手本人の情報には届かない。

### 次の仮説：相手について問いかければ、思い出せる（Phase3 相談モード）

| 打ち手 | 相手の情報を取りに行けるか | 判断 |
| --- | --- | --- |
| **相談モード（相手について問いかける）** | **直接取りに行ける** | **採用（核）** |
| 特集記事を増やす | 取りに行けない。150通りのうち約40通りしか届かず、1本3人日 | 補う手段として残す |
| ランキングを変える | 取りに行けない。D さんはランキングでは決められなかった | 採らない |
| Phase1 タグ付け・Phase2 モーダル | 一部。上の結果のとおり | 土台として残す |

相談モードの流れ：

1. 生成AIを使うかを、利用者が選ぶ（最初は使わない状態）
2. 「誰に贈りますか？」→「どんな場面ですか？」→「その方が最近『欲しい』『便利そう』と言っていたものや、困っていたことはありますか？」と問いかける
3. 3問目の答えを、DB にあるタグの言葉に置き換える（例：「やかんでお湯を沸かすのが大変そう」→「ケトル」）
4. タグに合う商品を DB から取り、理由（どの答えに合ったか）とあわせて返す

置き換えの役目は、顧客の言葉を DB のタグに翻訳することだけ。選べる言葉は DB にある決まった一覧に限り、商品は DB からだけ取る。

1つの仕組みで、複数の問題を解ける。

| 誰の問題 | 今の問題 | 相談モードで変わること |
| --- | --- | --- |
| 顧客 | 決めきれず離脱する | 決め手を思い出し、決めきれる |
| Giftia | 購入率 3.6% → 3.0% | 決めきれる人が増え、購入率が上がる |
| CS | 問い合わせの最多が「選択・用途」31% | 選び方の相談を、サイトの中で受けられる |
| 編集チーム | 記事は 150通りのうち約40通りしか届かない | 記事が届かない約110通りを、問いかけで補う |
| 商品部 | 新しいデータを付ける工数が足りない | 新しい表を作らず、既存のタグとレビューを使う（BR-04） |

### 作って分かった性能の課題

Phase1 でタグを作る処理を足したところ、検索が遅くなった。原因は毎回の DB 接続（新しい接続と SSL）で、接続プールで使い回し、検索1回を 5.6秒 → 約1.28秒にした。目標の1秒は、開発の段階で返す。

## 4. これからの検証：関門と撤退ライン

### 進め方

| 段階 | やること | 終わりの条件 |
| --- | --- | --- |
| 0. PoC と置き換えの検証（着手中） | 贈る予定のある人 5〜10人に、3問を口頭かフォームで聞く。決め手が出たか、何個目で「これにする」と言ったかを記録する。集めた答えとタグ一覧で、置き換えの正解率を測る | G0 を通る |
| 1-a. ログの実装 | 組（A/B）・表示・購入・検索語のログを作る。本番で全員に同じ画面を出したまま組だけ分け、差が出ないことを確かめる（A/A テスト）。今の購入率（比べる元）も測る | A/A テストで差が出ない |
| 1-b. 相談モードの実装（1-a と並行） | PoC の答えを試験データにして作る。生成AIかベクトル検索かは、この試験データで、正解率・答えの再現性・料金を比べて選ぶ | 置き換えの正解率が線を超える。応答時間の上限を守る |
| 2. A/B テスト（3か月） | 家族への誕生日から出す。1人ずつ組を固定する | G1 を判定する |
| 3. 調整（A/B の後） | 相談の答え・提示した商品・閲覧・購入のログで、置き換えを調整する | — |

- 1-a と 1-b を並行できるのは、相談モードを作るのに要る「ユーザーの言葉」を PoC で集められるため。相談モードの答えは、相談モードを出すまで誰も入力しないので、ログを先に作っても集まらない
- ログは A/B テストの開始より前に完成している必要がある。ログがないと、組と購入を結べず判定できない
- 開発の期間（1-a・1-b）は未確認。開発部の見積もりを待つ

### 関門

| 関門 | 測るもの | 通過 | 撤退・やり直し | 損はどこまでか |
| --- | --- | --- | --- | --- |
| G0 PoC | 問いかけで決め手を思い出せるか。思い出した言葉をタグに結べるか | 6割以上が決め手を1つ以上出し、その過半が決めきれる。置き換えの正解率の線は PoC の前に班で決める【要確認】 | 問いを1回だけ直してやり直す。それでも届かなければ作らず、課題を考え直す | 班の数日分 |
| G1 A/B テスト | B の組の1人あたり購入率（A の組との差） | A の組より有意に高い。見張る指標（カート放棄率・応答時間・他の導線からの購入）が悪化しない。増える売上が運用費（生成AIの料金など）を上回る | 機能フラグで止め、今の画面に戻す | 開発費（見積もり待ち） |
| G2 広げる判断 | B の組の購入率 | 3.0% に届く → 他の相手・場面に広げる | 届かない → 改善して再テスト（1回まで） | 改善の工数 |

- **撤退か継続かと、目標を分ける理由**：2.3% → 3.0% は +0.7pt で、試算の上振れのケースにあたる。3.0% に届かなければ撤退とすると、改善して利益が出ていても捨てることになる。そのため、撤退か継続かは G1、目標は G2 で判断する
- **+0.35pt の位置づけ**：合格の線ではなく、3か月のテストで見分けられる最小の差（必要なセッション数の前提）。試算の基準のケースでもある
- **運用費の条件**：運用費は未確認。1-b で1回あたりの料金を測ってから、数字を入れる
- **3.0% を B の組で見る理由**：全員に出していない段階では、家族への誕生日の全体の購入率は 3.0% にならない
- **主な指標を1人あたりの購入率にする理由**：セッションあたりの購入率は、早く買うだけの人でも上がるため、副の指標にする
- **A/B テストを3か月にした根拠**：+0.35pt を見分けるには、片側 約3.1万セッション。到達率 30% なら約2か月（261122版 6.2）。余裕を見て3か月にした
- **置き換えの前提**：タグ一覧をどの列から作るかは【要確認】。「家電」のような大きな分類しかないと、家電がまとめて出てしまい、絞り込めない

## 5. 投資判断とリスク

### 効果

売上増分 ＝ 対象 115.2万セッション × 到達率 × 改善幅 × 単価 5,400円。対象と単価は事実、到達率と改善幅は仮定。

| ケース | 到達率 | 改善幅 | 売上増分（年） |
| --- | --- | --- | --- |
| 下振れ | 30% | +0.1pt | 約190万円 |
| 基準 | 30% | +0.35pt | 約650万円 |
| 上振れ | 100% | +0.7pt | 約4,355万円 |

PoC の費用は、班の数日分。開発費・運用費・生成AIの料金は未確認で、1-b で1回あたりの料金を測り、開発部の見積もりとあわせて示す。

### リスクと打ち手

| リスク | 影響 | 打ち手 |
| --- | --- | --- |
| 仮説が外れる（根拠は D さんと4人の話） | 購入率が上がらない | G0 と G1 で早めに止める |
| 置き換えがうまくいかない | 相手に合わない商品が出る | 実装の前に、PoC の答えで正解率を測る（G0） |
| 生成AIの暴走 | 信頼を失う | 質問は固定。AI はタグの一覧から選ぶだけで、商品は DB からだけ取る。外部のリンクは出さない |
| 第三者（贈る相手）の情報を外部の AI に送る | 情報漏洩、信頼を失う | 送る情報の決まりを別に定める（名前など個人を特定できる情報は送らない、など）【要確認】 |
| 費用が見えない | 投資の回収が判断できない | 1-b で1回の料金を測る。OpenAI の管理画面で利用上限を設定する。ベクトル検索なら料金はかからない |
| 効く範囲が狭い（母のタグは 312商品） | 効果が小さい | 広げる前に、全ての相手のタグを付ける |

### 3問目の答えの保存

3問目の答えは、答えた本人が来年また贈るときに役立つ。ユーザーの入力を保存する同意は取っている前提で、保存する方向に変える。要件定義書の NFR-05（入力を保存しない）は、別の PR で直す（9章）。保存する同意と、外部の AI に送ることは別の問題として扱い、送る情報の決まりは上のリスクの表で定める。

| ④ A/B テスト（3か月） | 家族への誕生日から出す | G1 | 開発部・マーケ |
| ⑤ 広げる | 他の相手・場面に広げる。撤退なら機能フラグで止める | G2 | 開発部 |

### ログの中身

| ログ | 使い道 |
| --- | --- |
| 組（A/B）・表示・購入 | A/B テストの判定 |
| 検索語（どんな言葉で探したか） | どの段で離脱しているかを確かめる。0件の言葉からタグを足す |
| 相談の内容（3問の答え） | 置き換えの精度を上げる。本人が次に贈るときに使う |
| 提示した商品を見たか・買ったか | 相談モードが思ったとおりに働いているかを確かめ、調整する |

「全員が決めきれないのか」は、このログで、どの段で離脱しているかを見て確かめる。

**引き継ぎ資料**：要求定義書・要件定義書・仕様設計書と、この企画書の付録。開発部が着手する前に閉じる項目（相談モードの理由を誰が作るか、タグ一覧の作り方と元の列、`/api/consult` の名前、入力の長さの上限、料金と回数の上限、外部の AI に送る情報の決まり、ログの要件）は、担当と期限を決めて引き継ぐ。

## 7. 7分の台本

| 時間 | パート | 伝えたいこと（一言） |
| --- | --- | --- |
| 0:00–0:40 | 一言 | 相手に合う商品を決めきれない人に、相手との思い出を問いかけ、決め手を引き出す。今日決めてほしいこと |
| 0:40–1:40 | 事実 | 人は来て商品も多く見ているのに、選べずに帰っている。言ったことと決め手がずれている |
| 1:40–2:30 | 課題 | 決め手は相手についての情報。選ぶ場で思い出せず離脱し、購入率を下げている。解く範囲は思い出し型 |
| 2:30–4:00 | 仮説検証のストーリー | 他の人の買い物を見せたが、思い出せなかった。足りないのは相手の情報。だから問いかける |
| 4:00–5:20 | これからの検証 | PoC（着手中）→ ログと相談モードを並行して開発 → A/B テスト3か月。撤退ラインと目標を分ける |
| 5:20–6:20 | 投資判断とリスク | 下振れでも PoC の費用は小さい。リスクと保存の扱い |
| 6:20–7:00 | 決めてほしいこと | 開発と A/B テストへの投資の承認（PoC の兆しが条件）、撤退ラインと判定者の合意 |

## 8. 想定問答（この版で足すもの）

| 質問 | 答えの要点 |
| --- | --- |
| 相談モードが本命なら、なぜ最初から作らなかったのか | 安く速く確かめられる順に試す計画で始めた。Phase1・2 で、他の人の買い物やレビューでは思い出せないと分かり、相手の情報を直接取りに行く問いかけが本命になった（3章） |
| 全員が決めきれないのか | 全員とは言っていない。どの段で離脱しているかも、ログで確かめる（6章） |
| 3.0% に届かなかったら撤退するのか | 撤退か継続かは、今より有意に改善し、運用費を上回るかで判断する。3.0% は広げるかどうかの目標（4章） |
| 生成AIは本当に要るのか。ベクトル検索ではだめか | PoC の答えを試験データにして、正解率・再現性・料金で比べて選ぶ（4章 1-b） |
| 生成AIが思い出した内容を商品に結べるか、どう確かめるか | PoC の答えとタグ一覧で、実装の前に正解率を測る（4章 G0） |
| 相手の情報を保存しなくてよいのか | 同意を前提に保存する方向に変える。外部の AI に送る情報の決まりは別に定める（5章） |
