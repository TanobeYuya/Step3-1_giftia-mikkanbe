# 想定問答集（Giftia 改善企画書）

[企画書](261122_Giftia改善企画書.md)の発表で、レビュー役（副社長・バックエンドエンジニア・データベースエンジニア）から出そうな質問と、答えの要点。質問は、各ロールが事前に挙げた「発表で見る観点」から作った。答えは「結論 → 根拠の数字 → 次の手」の順に、30秒以内で話す。★は本命の質問。

## 副社長（投資の価値・成功と撤退・リスク）

| # | 質問 | 答えの要点 | 企画書 |
| --- | --- | --- | --- |
| 1★ | 誰の何を解き、どの数字がいくら動くのか。1文で | 家族の誕生日に贈る人が、相手の一言を思い出せるようにする。購入率 2.3% を 3.0% に近づけ、売上は年 約650万円（基準）から 約4,355万円（上振れ） | 0章 |
| 2★ | 外れたらどこまで損をするのか。やめる基準は | 試作で失うのは班の数日分。本番は A/B テストで、B が A 以下か、見張る指標が悪化したら、機能フラグで止める。今の画面のまま戻せる | 6.2・8.2 |
| 3 | 数字のうち、事実と仮定はどれか | 対象 115.2万セッションと単価 5,400円は事実。到達率と改善幅は仮定。仮定で桁が変わる（下振れ 約190万円〜上振れ 約4,355万円）ので、A/B テストで先に確かめる | 8.1 |
| 4 | 記事を増やす、ランキングを変える、と比べてなぜこれか | 記事は1本3人日で、150通りのうち約40通りしか届かない。ランキングは D さんが見ても決められなかった。今回の案は、既存のタグとレビューで小さく始められる | 4章 |
| 5 | 新しい導線で買った人は、もともと記事やランキングから買っていた人では（食い合い） | くじ引きで A と B に分けるので、B の増加分は純増と読める。あわせて、B の組で記事・ランキングからの購入が減っていないかを見張る | 6.2 |
| 6 | 作った後の運用は誰が、月何人日でするのか | 贈る相手のタグは SQL で自動。新しい文や商品の確認は商品部で、Excel に選択肢から書くだけにする。BR-04 の枠（月15人日）に収まるかを 12月にすり合わせる | 9.3 |
| 7 | なぜ Giftia がやるのか。他社にすぐ真似されないか | 生成AIの仕組みは誰でも作れる。差は Giftia にしかないデータ（シーンのタグ、母に贈ったレビュー、贈った相手の分かる注文）と、それを更新し続ける運用 | 4章 |
| 8 | 課題の根拠は D さん1人。弱くないか | 弱い。そのため課題は「仮説」とし、試用で兆しを見て、A/B テストで数字を取る2段にした。課題の大きさ（115.2万セッション）は事実だが、確からしさはこれから確かめる | 2章・6章 |
| 9 | 生成AIで情報漏洩や暴走が起きないか | 質問の文と順番は固定。AI はキーワードを選ぶだけで、商品は Giftia の DB から取る。外部リンクは出さない。3問目の入力は保存しない | 7.3・8.3 |
| 10 | 今日、何を決めてほしいのか | ① 本番に向けた条件付き承認（試用の兆しと商品部の合意が条件） ② 12月の商品部とのすり合わせへの着手 ③ A/B テストの撤退ラインと判定者の合意 | 0章 |

## バックエンドエンジニア（処理の流れ・API・エラー・運用）

| # | 質問 | 答えの要点 | 企画書・根拠 |
| --- | --- | --- | --- |
| 1★ | 入力から返却まで、どこで何をしているか | 画面が条件を送る → API が値を確かめる（選択肢以外は 422）→ SQL で件数と上位20件を取る → タグを最大5個作る → `{ total, results }` で返す。番号つきの流れはアーキ図の①〜⑩ | 7.2・Appendix B |
| 2★ | 0件、未入力、不正な値のとき、どう返すか | 0件は 200 で空の一覧（エラーとは分ける）。条件なしは今までと同じ販売数の順。選択肢以外の値や101文字の q は 422、ない商品 ID は 404。SQL やスタックトレースは返さない（TC-19） | 7.3 |
| 3 | 生成AIが落ちたら、相談モードはどうなるか | エラーで止めず、相手と場面だけで探した結果を返す（P2-18）。AI への問い合わせは3問に答えたあと1回だけ | 7.3 |
| 4 | 同点のとき、並び順は一意に決まるか | 母へのレビュー件数 → 販売数 → 商品 ID の順で並べるので、最後は商品 ID で必ず決まる。同じ入力なら毎回同じ順 | 7.3 |
| 5 | JOIN で行が増えて、数え間違えないか | シーンの絞り込みは EXISTS にしたので、1商品に複数のシーンがあっても行は増えない。件数（total）と表示件数（20件）は別に数えている | 7.2 |
| 6 | 検索が遅い原因は何で、どう直したか | 検索1回 約5.4秒のうち、接続が約4.6秒（毎回の新しい接続と SSL）。接続プールで使い回し、約1.28秒にした。目標の1秒は Phase3 以降に申し送り | 7.2 |
| 7 | タイムアウトや、詰まったときの止め方はあるか | DB の接続には10秒のタイムアウトがある。プールが満杯のときの待ちには上限がなく、受け入れたリスクとして残している。本番前に上限と 503 を決める | 9.2 |
| 8 | 接続情報や API キーはどこに置いているか | `.env` と関数アプリの環境変数だけ。画面側には置かない。GitHub には `.gitignore` で載せない。CORS は許可した画面の URL から GET だけ | 7.3 |
| 9 | 効果を測るためのログはあるか | ない。閲覧・検索語・表示・離脱の記録がないので、いまは迷いや離脱を再現できない。A/B の組と購入を結ぶログを、本番の開発で足す | 6.2・9.2 |
| 10 | どこまで実装済みで、どこからが未実装か | 実装・テスト済みは Phase1 と Phase2 ①。相談モード（②）は 11/24 までに実装中で、発表で動くかは未確認。ベクトル検索（③）は作らない | 5章 |

## データベースエンジニア（データモデル・整合性・性能・運用）

| # | 質問 | 答えの要点 | 企画書・根拠 |
| --- | --- | --- | --- |
| 1★ | どの表を、何のために、どう変えたか | 表と列は増やさず、product_facts に review_to_mother の行を 312商品分足した（Phase1）。新しい表は review_sentences だけ（Phase2 ①）。ER 図は変更前と変更後を同じ配置で並べてある | 7.1・Appendix C |
| 2★ | 足したデータは誰がどう作り、どう確かめたか | review_to_mother はレビュー本文を SQL で集計し、無作為20件の目視で誤り2件以下を基準にした。文の辞書は AI が案を出し、人が確認した。TC-17・18 で 824件・87文の不一致 0件 | 7.1・9.3 |
| 3 | なぜ新しい表ではなく、product_facts に行を足したのか | 既存の「商品の事実」の形（product_id・fact・value・source）にそのまま乗り、既存の行と列に手を触れずに済む。source 列で作り方を分けられる | 7.1 |
| 4 | 1つの列に複数の意味を入れていないか | product_facts の value は、fact によって 0/1・件数・日数と意味が違い、CHECK 制約もない。問題として認識しており、本番前に fact ごとの値の範囲を制約かテストで守る | 7.1・9.2 |
| 5 | 「不明」と「いいえ」を区別しているか | 個包装などは、行がない＝不明、0＝いいえ、1＝はい と分けている。一方で、評価が NULL の商品を API が 0 で返しており、本番前に「評価なし」と出すよう直す | 7.1・9.2 |
| 6 | 同じ事実を2か所に持っていないか | products の rating・review_count・sales_count と review_to_mother は、元データの集計を別に持っている。速さのための意図的な選択で、ずれないよう月1回作り直す。本番ではジョブにする | 7.1 |
| 7 | 件数が増えたら、検索は耐えられるか | いまは 8,000件を全件読み、DB の中は 73ms。件数が10倍になると全件の読み込みも増えるため、EXPLAIN を見て、絞り込みに使う列と product_facts の（fact, value）にインデックスを検討する | 7.2 |
| 8 | SQL インジェクションをどう防いでいるか | 値はすべてプレースホルダー（%s）で渡し、文字列に直接つながない。選択肢の値は API の入口で決めた値以外を 422 にする。`G0001;DROP` などを送っても 422 で止まる（TC-19） | 7.3 |
| 9 | 誤ってデータを消したら戻せるか。権限は | 追加データは SQL とファイルから作り直せる。取り込みは START TRANSACTION〜COMMIT で囲んでいる。Azure の自動バックアップの保持期間は未確認。本番では、アプリは SELECT だけのユーザーにする | 9.2 |
| 10 | シーンやタグを増やすとき、直す場所は1か所で済むか | 今は済まない。マスタ表がないので、シーンを1つ足すのに DB・API・画面の3か所を直す。本番前にマスタ表にし、1か所で済むようにする | 9.2 |
